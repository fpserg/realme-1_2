## 1. Purpose and authority

This roadmap extends the accepted RealMe 1.2 founding sequence into bounded substantive product implementation. It governs the sequence from the Step 96 infrastructure foundation to a perceivable and constitutionally faithful RealMe 1.2 MVP.

Roadmap acceptance does not begin any implementation step, provision an external resource or accept the result of a future step. Each step requires a separately bounded scope, verified implementation and explicit Warden acceptance.

## 2. MVP acceptance definition

RealMe 1.2 reaches MVP when a new user can:

1. sign in and receive one private World and one companion;
2. tell RealMe something that happened or needs attention;
3. have the observation preserved before AI processing;
4. see it assigned to the correct operational period;
5. receive a useful companion response;
6. review any proposed durable interpretation separately;
7. accept, reject or correct that interpretation;
8. see accepted understanding reflected in Today and the code-native Living World;
9. reload the app without losing identity, provenance or history.

A chat shell, static dashboard or painted map alone does not qualify.

## 4. Accepted implementation sequence

### Step 97 — Environments, Authentication and World Ownership

Provision the authorized Netlify and Supabase environments.

Deliver:

- Supabase Auth;
- private user account;
- one World per initial owner;
- World membership and ownership boundaries;
- Row-Level Security;
- automatic creation of one companion;
- isolated synthetic preview environment.

Acceptance gate: authenticated users cannot access another World through either UI or direct API requests.

### Step 98 — Canonical Truth Schema

Introduce the first constitutional database migration.

Deliver:

- observations and exact source fragments;
- provenance and attachment metadata;
- interpretation runs and candidate claims;
- admissions, rejections and corrections;
- ontology nodes, aliases and relationships;
- versioned assertions;
- time settings and operational periods;
- jobs and audit records;
- stable identities independent of names or classification.

Acceptance gate: observation, interpretation, admission and World Model state are demonstrably separate.

### Step 99 — Persist-First Observation Capture

Build the first real vertical slice.

Deliver:

- mobile input surface;
- authenticated capture command;
- occurred-time entry and correction;
- recorded-time assignment;
- idempotency protection;
- visible saved, processing, failed and unsynced states;
- reload-safe observation history.

Acceptance gate: an observation survives even if AI processing fails completely.

### Step 100 — Native Temporal Continuity

Implement the accepted time model.

Deliver:

- user timezone;
- default 04:00 operational boundary;
- local calendar date;
- operational-period membership;
- late observation handling;
- prospective boundary changes;
- audited historical correction;
- initial Today timeline.

Acceptance gate: no manual Freeze is required and changing the boundary does not silently rewrite history.

### Step 101 — One-Companion Dialogue

Create the first useful companion experience.

Deliver:

- one companion without an imposed Realmer roster;
- mobile-first dialogue;
- server-side model-provider abstraction;
- authorized context assembly;
- streaming response;
- evidence-fragment preservation;
- conversation archive off by default;
- graceful provider failure.

Acceptance gate: dialogue can respond meaningfully but cannot mutate canonical understanding directly.

### Step 102 — Interpretation and Durable Job Pipeline

Connect persisted observations to governed AI processing.

Deliver:

- durable interpretation jobs;
- structured candidate output;
- exact evidence links;
- model, prompt and schema versioning;
- deterministic validation;
- retry and idempotency;
- hidden unresolved candidates;
- complete run provenance.

Acceptance gate: duplicate delivery cannot create duplicate observations, candidates or canonical changes.

### Step 103 — Admission and Versioned World Model

Implement RealMe’s constitutional decision boundary.

Deliver:

- candidate review cards;
- accept, reject, correct and defer actions;
- transactional admission;
- versioned assertions;
- stable node identity through reclassification;
- supersession without erasure;
- conservative structural evidence policy;
- explicit acceptance for every Realm discovery.

Acceptance gate: no AI-generated interpretation becomes canonical without passing admission policy.

### Step 104 — Commitments and Operational Projections

Turn memory into visible continuity.

Deliver:

- Today;
- near-term Horizon;
- commitments and occurrences;
- operational-period history;
- source-linked provenance;
- rebuildable projections;
- late updates without manual closing rituals.

Acceptance gate: projections can be destroyed and rebuilt from canonical records without changing truth.

### Step 105 — Code-Native Living World

Establish the universal World substrate before image generation.

Deliver:

- stable hierarchy and arbitrary-depth navigation;
- topology independent of illustration;
- code-native node representation;
- semantic approach and outward navigation;
- no empty Realm or Domain slots;
- no discovery counters or completion percentages;
- unformed World state for new users;
- visible structure only after acceptance.

Acceptance gate: the World remains understandable and navigable with zero generated images.

### Step 106 — Integrated Perceivable Experience

Unify the components into the first recognizably RealMe application.

Primary surfaces:

- **Companion**;
- **Today**;
- **World**.

Complete loop:

```text
Expression
→ Observation saved
→ Companion response
→ Candidate interpretation
→ User admission
→ World Model update
→ Today and World reproject
```

Acceptance gate: this loop works end to end on a mobile viewport and survives a full reload.

**This is the first perceivable universal RealMe 1.2 MVP checkpoint.**

### Step 107 — Sergey Pilot Migration

Validate the universal system against the mature founding instance.

Deliver:

- explicit migration tooling;
- selected historical observations and commitments;
- accepted personal ontology with stable imported identities;
- mapping of validated canonical visual masters;
- Sergey-specific visual definition;
- provenance for every imported record;
- no use of `initialStore.ts` as a production seed.

Acceptance gate: Sergey’s instance remains canonical without becoming the onboarding template for other users.

### Step 108 — Authored World Viewer

Adapt the proven 1.1 interaction lessons to the modular architecture.

Deliver:

- World → Realm → deeper-node semantic navigation;
- independent anchor, hit-region and entry-focus geometry;
- pan and pinch inspection within a level;
- adaptive framing distinct from semantic zoom;
- Sergey’s validated paintings as geography;
- code-controlled semantics;
- code-native fallback when artwork is absent.

Acceptance gate: Sergey’s authored World and a blank new-user World both operate through the same universal semantic system.

### Step 109 — MVP Hardening and Acceptance

Prepare the system for sustained personal use.

Deliver:

- complete authorization-policy tests;
- export and deletion foundations;
- private asset access;
- personal-content-safe logging;
- accessibility validation;
- mobile browser coverage;
- recovery and projection-rebuild tests;
- deployment preview;
- end-to-end constitutional regression suite;
- independent Code Review.

Acceptance gate: Architect review, Code Review clearance and explicit Warden acceptance.

**Step 109 acceptance establishes RealMe 1.2 MVP.**
